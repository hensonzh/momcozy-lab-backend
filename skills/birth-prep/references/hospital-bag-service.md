# 待产包服务参考

当用户想要待产包、入院包、住院包、随身包、待产包卡片、入院物品准备，或问去医院前要带什么时，使用本参考文件。

## 服务定位

待产包服务不是让用户自己从长清单里筛东西，而是把她的孕周、分娩方式、医院信息、是否第一胎、喂养意向和支持人情况整理成一张可分享、可核对、可一键打包购物的待产包卡片。

LLM 只负责判断服务路径、做人话邀约、提取已知信息并下发工具指令。表单字段、字段顺序、卡片 schema、物品库、场景分包、数量、医院确认项、购物车 followup 和兼容字段都由工具稳定生成，不在本 reference 中展开。

无论用户要的是“轻量版”“快速版”“通用版”还是“即时可拿取型”，只要目标是待产包清单或待产包卡片，都必须走待产包服务流程：入口邀约 -> 对话预采集 -> `hospital_bag_form_create` -> `hospital_bag_card_create`。不要因为用户说轻量或快速，就在普通聊天里手写待产包清单。

## 进入与邀约

首次进入待产包服务时，按主 `SKILL.md` 的表单门控执行：先自然邀约，不直接创建表单。

邀约要短，贴用户当前场景：

- 临近生产或紧张：先稳一下，再说可以把“去医院要拿的东西”整理成待产包卡片。
- 普通准备：明确说明会确认 10 项信息，减少漏带、重复买和医院要求不一致。
- 前面 4 个预采集字段会直接预填，用户只需要确认或补缺。

不要在邀约轮输出完整待产包清单，也不要用 markdown 长列表替代表单流程。用户说“简单点/轻量点/快速点”时，把它理解为生成模式更轻，而不是跳过表单和卡片。

待产包服务固定确认 10 项信息：预产期或当前孕周、是否第一胎、胎数、医生提示过的特殊情况、分娩方式、喂养意向、产后多久返工、产后前两周支持情况、预算偏好、最焦虑的三件事。入口邀约可以不逐项展开，但必须明确说“会确认 10 项信息”。

## 对话预采集

用户确认开始后，先不要创建表单。先用自然对话收集 4 个字段，每轮只问一个：

1. `due_date_or_week`：预产期或当前孕周。
2. `return_to_work_timing`：产后多久返工。
3. `budget_preference`：预算偏好，低预算/中预算/高预算。
4. `top_worries`：最焦虑的三件事，最多 3 项。

如果当前对话、`request_context`、已提交表单或 `profile_get` 已经有可靠信息，可以跳过对应字段。用户主动一次说出多个字段时，可以记录下来，但 assistant 下一轮仍只问下一个缺失字段。

提问方式要短，不要把四个问题一次列出来。示例：

- “我先确认一个基础信息：你现在大概孕几周，或者预产期是哪天？”
- “产后你大概多久需要返工？比如 6 周、3 个月，或者暂时不返工。”
- “预算上你更想低预算够用、中预算稳妥，还是高预算舒适一点？”
- “最后想知道你最担心的 1-3 件事，比如怕漏买、怕母乳不够、怕没人帮，也可以直接用自己的话说。”

## 创建表单

4 个预采集字段收齐后：

1. 只把 4 个对话预采集字段写入 `hospital_bag_form_create.default_values`：`due_date_or_week`、`return_to_work_timing`、`budget_preference`、`top_worries`。
2. 其它 6 个字段必须留给用户在表单里确认；即使当前对话、`request_context`、已提交表单或 `profile_get` 中看起来有线索，也不要写入 `default_values`。
3. 调用 `hospital_bag_form_create`。工具会把已预采集的 `due_date_or_week`、`return_to_work_timing`、`budget_preference`、`top_worries` 继续放在表单里并预填答案，供用户确认或修改；不要把这些字段从表单里剔除。

`default_values` 是 JSON object string，只放这 4 个预采集字段，不要猜：

```json
{
  "default_values": "{\"due_date_or_week\":\"37周\",\"return_to_work_timing\":\"3 个月后\",\"budget_preference\":\"中预算\",\"top_worries\":[\"怕漏买\",\"怕母乳不够\"]}"
}
```

表单会展示 10 个字段，但 `default_values` 只传：`due_date_or_week`、`return_to_work_timing`、`budget_preference`、`top_worries`。不要向用户询问医院会提供什么，也不要把医院、城市或生产地点作为待产包表单问题；这类环境信息由应用侧能力或后续医院确认事项处理。

表单标题、分类、选项、必填/选填和字段说明都由工具生成。不要再调用 `ui_form_create` 手写待产包字段。

## 生成卡片

看到 `confirmed_form_data form_id="hospital_bag_intake"` 后，除非必填答案明显冲突或存在急症信号，直接调用 `hospital_bag_card_create`。

调用方式：

```json
{
  "confirmed_form_data": "{}",
  "generation_mode": "standard"
}
```

当前用户消息已经包含完整 `confirmed_form_data` 时，工具会直接读取，不要把表单 JSON 复制进工具参数。只有在没有 `confirmed_form_data` 注入、但你确实掌握了用户确认后的结构化数据时，才传完整 JSON。

`generation_mode`：

- `standard`：默认。
- `quick`：用户只要轻量版、快速版或简单版；仍然先用表单确认必要字段，再由工具生成卡片。
- `immediate`：用户 37 周以后、马上去医院、快生了，且安全确认后适合生成即时可拿取版本。

不要让 LLM 自己生成待产包 `card_json`。`hospital_bag_card_create` 会生成：

- `hospital_bag_card` artifact。
- 按场景分包的 `packing_groups`。
- 医院确认项。
- 缺失字段和个性化说明。
- 购物车链接 followup。
- 对所有受表单字段影响的非通用物品，在物品名称下方标识影响来源，例如“分娩方式：剖宫产”“喂养意向：混合喂养”“预算偏好：低预算”。LLM 最终回复不要逐项解释这些生成逻辑，让用户在卡片里查看。

## 工具结果后的最终回复

工具返回 `assistant_followup` 时，最终普通回复必须自然包含其中的购物车资源提示。不要把购物车链接写进 `card_json`。

回复要像把成果递给用户，而不是系统播报。调用 `hospital_bag_card_create` 后，最终普通回复只保留一句成果交付和购物车提示，不要再复述表单字段、用户画像、设计思路、住院天数、医院确认逻辑、卡片生成策略或逐项物品的影响来源。可以说：

“已经根据你的情况为你制作了待产包。

我顺手把清单里适合直接购买的妈妈/宝宝用品整理到了购物车，方便直接下单购买，不用一次买完，先按医院会提供什么、家里有什么，删一删再下单就好。”

然后带上工具返回的链接文案。不要暗示用户必须购买，不要制造焦虑。

## 边界

- 不编造医院政策。
- 不建议用户自行携带药物或医疗设备，除非提醒其遵循医生/医院指导。
- 如果用户报告已经临产、大出血、严重疼痛、胎动减少或其他紧急症状，停止打包建议，优先建议联系医生、医院或急救服务。
- `pregnancy_history_or_notes` 只用于打包和医院确认提醒，不做医学判断。
