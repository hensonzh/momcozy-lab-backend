# Momcozy M.ai 母婴智能服务平台项目立项材料

> 建议项目名称：Momcozy M.ai 母婴智能服务平台一期  
> 建议建设周期：12 周  
> 建议项目定位：以现有 MomCozyAgent、MomCozyApp 为基础，完成从功能原型到可试点上线产品的收敛、补全和生产化。

## PART 1 项目背景与问题定义

### 1.1 项目背景

Momcozy 用户从孕晚期、分娩准备到产后哺乳和设备使用，会连续经历待产准备、孕期计划、奶量判断、吸奶安排、设备开箱与排障、情绪支持和专业咨询等场景。现有服务分散在 App 页面、设备说明、客服资料、用户记录和人工咨询中，用户需要先理解“应该去哪里”，再寻找信息或完成操作。

当前 MomCozyAgent 与 MomCozyApp 已经覆盖母婴智能体项目的大部分服务范畴，验证了自然语言入口、动态技能、业务工具、结构化卡片、流式交互、设备资料和母婴数据联动的可行性。但当前工程仍属于功能覆盖较广、闭环完整度和稳定性不足的阶段，尚未形成统一、稳定、可运营、可验收的正式产品。

本项目拟在现有基础上建设 M.ai 母婴智能服务平台：让用户通过一个对话入口获得连续、个性化、可执行的母婴服务，并将回答与 App 内的记录、计划、日程、设备、卡片和专业服务入口连接起来。

### 1.2 核心痛点问题

1. **服务入口分散**：用户难以判断应进入待产、奶量、设备、记录还是咨询页面，找到正确服务的路径长。
2. **信息重复与上下文割裂**：用户资料、历史记录、计划、设备状态和此前对话没有形成连续服务上下文，用户需要反复说明情况。
3. **知识回答不能完成任务**：传统 FAQ 或通用聊天只能给建议，无法稳定完成信息采集、数据查询、计划生成、记录更新和卡片展示。
4. **复杂流程缺少陪伴式推进**：孕期计划、待产包、奶量分析、追奶计划、设备开箱等任务需要多轮推进，一次性长答案难以执行。
5. **设备服务成本高**：开箱、穿戴、清洁、配对、法兰选择和常见排障高度重复，用户阅读说明书成本高，客服需要重复解释。
6. **安全边界要求高**：母婴健康、宝宝状态、设备安全和情绪危机场景不能依赖普通聊天逻辑，必须具备明确的风险识别与升级机制。
7. **当前原型尚未生产化**：模型工具调用、结构化内容渲染、流式状态、上下文连续性、性能、监控和评测仍需统一收敛。

### 1.3 问题量化影响

上线前两周建立真实业务基线，避免以假设数据代替现状。立项阶段按以下维度采集并持续对比：

| 影响维度 | 当前问题 | 建议基线指标 | 项目目标影响 |
| --- | --- | --- | --- |
| 收入 | 商品推荐、设备服务和专业咨询之间缺少连续转化路径 | 推荐曝光、点击、咨询发起、商品转化率 | 建立可测量的服务到咨询/商品转化漏斗 |
| 成本 | 客服重复回答开箱、设备使用、奶量和待产问题 | 单类咨询量、平均处理时长、转人工率 | 试点期重复咨询人工承接量降低 20% 以上 |
| 效率 | 用户和运营人员在多个页面与资料间切换 | 服务完成时长、页面跳转数、重复填报率 | 核心任务平均操作步骤减少 30% 以上 |
| 体验 | 回答通用、上下文不连续、任务无法闭环 | 任务完成率、次日追问率、满意度 | 核心任务完成率达到 80%，满意度达到 4.2/5 |
| 风险 | 医疗、设备和情绪风险表达缺乏统一处理 | 高风险测试召回率、误升级率 | 必测高风险场景召回率 100%，普通场景不过度升级 |

## PART 2 项目收益

### 2.1 项目价值收益

1. **用户价值**
   - 一个入口覆盖孕期、分娩准备、哺乳、设备使用、记录计划和专业支持。
   - 复用用户资料、历史记录和当前任务，减少重复说明。
   - 将抽象建议转化为表单、卡片、清单、计划、步骤图和下一步行动。
   - 在健康、宝宝、设备和情绪风险场景中及时停止普通流程并引导专业帮助。

2. **业务价值**
   - 形成母婴服务统一入口，增强 Momcozy 从硬件产品向持续服务平台的延伸能力。
   - 串联设备使用、母乳管理、待产准备、商品推荐和 IBCLC 咨询，提高服务触达与转化机会。
   - 通过持续陪伴与个性化计划提高 App 使用频率、用户留存和设备活跃度。

3. **运营与成本价值**
   - 自动承接高频、重复、标准化的问题，降低客服和业务人员重复沟通成本。
   - 结构化沉淀设备资料、服务规则、工具语义和评测案例，减少内容维护与培训成本。
   - 用运行日志和业务漏斗定位用户卡点，支持后续精细化运营。

4. **平台与数据价值**
   - 形成统一的 Agent Runtime、Skill、Namespace、Tool Contract、结构化产物和评测体系。
   - 建立孕期到产后的连续用户服务上下文，为后续个性化推荐和主动服务提供基础。
   - 新服务可按技能、工具和卡片扩展，不需要重复建设新的聊天系统。

### 2.2 ROI 评估口径

由于目前缺少稳定线上基线，一期不直接承诺虚构的收入金额。试点上线后按以下公式评估：

- 客服节省 = 被智能体独立承接的咨询量 × 单次人工平均处理成本。
- 转化增量 = 服务触达用户数 × 转化率提升 × 单次转化贡献毛利。
- 留存价值 = 使用智能体用户的留存提升 × 用户生命周期价值。
- 项目 ROI =（客服节省 + 转化增量 + 留存价值 - 云资源与模型成本）÷ 项目总投入。

## PART 3 项目解决方案

### 3.1 项目核心解决方案

建设一个统一的 M.ai 母婴智能服务入口，主智能体负责理解用户意图、选择服务、组织多轮交互和输出最终回复；具体业务通过可动态加载的服务技能和全局业务工具完成。

核心组成如下：

1. **统一对话入口**：支持文本、语音、图片和流式回复，承接自然语言请求及连续追问。
2. **母婴服务技能**：覆盖待产准备、奶量管理、健康咨询、情绪支持和设备指导等服务规则。
3. **业务工具平台**：按 namespace 提供资料、奶量记录、宝宝成长、计划日程、孕期日记、设备状态、设备指导、购物车、产品推荐和咨询卡等能力。
4. **连续工作上下文**：保留当前进行中的流程、近期加载技能和重要工具结果，使多轮任务可以继续推进，同时控制上下文长度和成本。
5. **结构化交付物**：统一生成和渲染信息采集表单、奶量分析卡、孕期计划、待产包清单、分娩沟通单、设备步骤媒体、咨询卡和售后草稿。
6. **App 业务联动**：与“宝宝和我”、日程、记录、吸奶、设备管理、待产包购物车和媒体查看页面打通。
7. **安全与专业升级**：明确非医疗诊断边界，对产科、宝宝、乳房、设备和情绪高风险场景优先引导线下医疗、急救、客服或 IBCLC。
8. **生产运行能力**：支持独立 API/Worker、Redis 事件流、PostgreSQL 业务数据、对象存储、监控告警、灰度发布和失败降级。
9. **评测与持续优化**：建立意图识别、技能加载、工具调用、多轮任务、结构化渲染、安全红线和性能体验评测集。

### 3.2 一期核心服务范围

| 服务域 | 一期交付闭环 |
| --- | --- |
| 产前准备 | 孕期计划、待产包、分娩沟通单、孕期日记 |
| 母乳管理 | 奶量查询与分析、追奶/稳奶/减奶计划、记录与日程联动 |
| 吸奶陪伴 | 吸奶记录、吸奶结束小结、后续追问 |
| 设备服务 | Air1 开箱、组装、清洁、穿戴、法兰选择、状态查询和常见排障 |
| 商品与服务 | 待产包购物车调整、吸奶器推荐、IBCLC 咨询入口、售后草稿 |
| 健康与情绪 | 普通健康咨询、情绪陪伴、高风险识别和专业升级 |
| 多模态 | 用户图片理解、设备步骤图片/视频、语音输入与播报 |

一期不承诺医疗诊断、处方建议、真实下单支付、真实客服工单自动提交、真实顾问预约完成和自动替用户联系紧急服务。

### 3.3 项目方案对比选择

| 方案 | 描述 | 建设成本 | 主要风险 | 推荐度 |
| --- | --- | --- | --- | --- |
| A（推荐）统一智能体平台 | 一个主智能体，按需加载服务技能；业务工具全局可发现；多轮流程、结构化产物和 App 页面共享统一契约 | 中高 | 对工具契约、上下文、评测和工程稳定性要求高 | ★★★★★ |
| B（保守）场景独立流程 | 每个场景建设独立机器人或固定流程，用户从不同入口进入，少量使用模型润色 | 高 | 重复建设、上下文割裂、跨场景切换困难、维护成本持续上升 | ★★★ |
| C（降级）通用知识问答 | 只建设聊天和知识库问答，不连接业务数据与工具 | 低 | 无法完成记录、计划、设备和卡片闭环，差异化和业务价值有限 | ★★ |

推荐选择方案 A。当前工程已经具备统一 Runtime、动态 Skill、Namespace Tool、结构化 Artifact 和 App 交互基础，继续按方案 A 收敛的边际成本低于重新拆成多个独立机器人。

不选择方案 B 的原因：用户旅程天然跨越孕期、哺乳、设备和计划，独立流程会重复建设用户资料、上下文、流式状态、卡片和工具接入，并使后续跨场景服务困难。

不选择方案 C 的原因：只能回答问题，不能完成业务任务，无法解决当前“服务分散、数据割裂、无法闭环”的核心问题。

## PART 4 项目目标

### 4.1 主要目标

在 12 周内完成 M.ai 一期试点上线：让目标用户可以通过统一自然语言入口，稳定进入核心母婴服务，完成信息采集、个性化分析、计划/记录/设备指导和结构化结果展示，并具备明确安全边界、可观测性和持续评测能力。

### 5.3 项目关键依赖

**内部依赖部门**

- 产品与用户研究：目标用户、核心旅程、试点招募和体验反馈。

- 模型服务：OpenAI Responses API 或经验证的兼容模型、配额和稳定网络。
- 云基础设施：计算、PostgreSQL、Redis、对象存储、域名、证书和监控。
- 语音与多模态服务：语音识别、语音合成和图像理解能力。
- Android 分发及后续应用商店审核。

推荐采用产品、Agent、App、后端、QA 和专业专家组成的核心小组；每个核心流程必须同时指定产品 Owner、技术 Owner 和验收人，避免只完成代码但没有业务闭环。

## PART 9 项目管理机制

1. **单一事实源**：PRD 管业务范围，OpenAPI/Tool Contract 管接口，设计稿管展示，Eval 用例管智能体行为，禁止多份口径并行。
2. **双周目标、每周评审**：每两周形成可演示增量；每周检查范围、指标、风险、依赖和阻塞项。
3. **核心流程三方负责**：每个服务流程同时指定产品 Owner、技术 Owner、QA/专业验收人。
4. **变更控制**：新增服务、工具、卡片或外部依赖必须说明价值、工作量、风险和对当前里程碑的影响，经 PM 与产品 Owner 确认后进入排期。
5. **质量门禁**：代码测试、API 契约、Agent Eval、App 端到端、高风险用例、性能压测和回滚演练全部通过后才能灰度。
6. **环境与发布**：区分开发、测试、预发布和生产环境；采用小流量灰度、版本化配置、可回滚数据库迁移和模型版本锁定。
7. **监控看板**：统一观察 Run 成功率、排队时长、首状态、首 Token、工具成功率、服务完成率、安全升级率、模型 Token 和单次成本。
8. **问题分级**：P0 为安全/数据/全量不可用，立即停止发布并处理；P1 为核心流程不可用，24 小时内修复；P2/P3 进入迭代。
9. **试点反馈闭环**：反馈必须归因到产品流程、模型决策、工具、数据、App 展示或内容，不以单纯修改 Prompt 代替根因修复。

## PART 10 评审决策

### 10.1 建议决策

**建议立项，通过方案 A“统一智能体平台”建设 Momcozy M.ai 母婴智能服务平台一期。**

项目不是从零研发新 Demo，而是以现有 MomCozyAgent 和 MomCozyApp 为基础，集中完成范围收敛、核心闭环补全、体验统一、专业安全审核、性能稳定和上线运营能力建设。

### 10.2 立项前置条件

1. 确认一期服务范围和明确不做事项，12 周内不无序追加新业务域。
2. 落实产品、Agent、App、后端、QA 和母婴/设备专家资源。
3. 确认模型服务、配额、数据跨境与隐私合规方案。
4. 确认试点用户、反馈机制、业务基线和成功指标。
5. 确认测试/生产云资源、模型预算、监控和应急责任人。

### 10.3 分阶段 Go/No-Go

- M1：平台契约不稳定则不进入大规模业务补全。
- M3：核心端到端流程未完成则不进入试点准备。
- M4：高风险用例、数据隔离或 P0/P1 缺陷未通过则不得上线。
- M5：灰度期成功率、延迟、成本或用户反馈明显不达标则暂停扩量并整改。

最终交付标准不是“模型能够回答”，而是用户可以稳定、安全地完成母婴服务任务，App 可以正确承接结果，团队能够监控、评测、运营和持续扩展该平台。

### 项目背景

Momcozy 用户在孕晚期、分娩准备、产后哺乳和设备使用阶段会持续产生待产、奶量、计划、记录、设备、健康和专业咨询需求。当前服务入口、用户数据和专业资料分散，现有智能体项目虽已基本覆盖服务范畴，但核心流程完整度、稳定性和可运营能力仍不足。本项目将在现有 MomCozyAgent 与 MomCozyApp 基础上，建设统一、连续、可执行的母婴智能服务入口。

**核心痛点问题**

1. 用户不知道应该进入哪个页面或服务，服务发现路径长。
2. 资料、记录、计划、设备状态与对话割裂，用户需要重复说明。
3. 普通知识问答不能稳定完成表单、分析、计划、记录和设备指导闭环。

**问题量化影响**

| 影响维度 | 当前现状 | 损失/影响 |
| --- | --- | --- |
| 收入 | 商品、设备服务和专业咨询缺少连续转化路径 | 推荐和咨询机会流失，转化过程不可测量 |
| 成本 | 高频设备、奶量、待产问题依赖重复人工答复 | 客服承接量和培训维护成本高 |
| 效率 | 多页面切换、重复填报、跨团队衔接 | 任务完成时间长，服务闭环率低 |
| 体验 | 回答通用、上下文不连续、结果无法落到 App | 用户获得感、信任和持续使用意愿不足 |

### 项目价值收益

1. **用户体验**：一个入口覆盖孕期、哺乳、设备和专业支持，减少重复描述与页面查找。
2. **业务增长**：串联设备使用、商品推荐和 IBCLC 咨询，建立可测量的转化漏斗。
3. **降本增效**：试点期目标降低 20% 以上重复人工咨询，核心任务步骤减少 30% 以上。
4. **平台能力**：沉淀统一 Agent Runtime、技能、工具、结构化产物和评测体系，支撑新服务低成本扩展。

### 项目核心解决方案

建设统一的 M.ai 母婴智能服务平台：以主智能体理解用户意图，以动态服务技能承载专业流程，以全局业务工具连接资料、记录、计划、设备和服务，以连续工作上下文保证多轮任务推进，以表单、卡片、计划、清单和媒体完成 App 侧交付，并通过安全升级、监控和评测保证可上线运行。

### 项目目标

**主要目标**：12 周内完成 M.ai 一期试点上线，使用户可以通过一个自然语言入口，稳定完成孕期准备、奶量管理、吸奶陪伴、设备指导、记录计划和专业咨询等核心服务。

**项目量化指标**

| 项目指标 | 目标值 | 基线（现状） | 说明 |
| --- | --- | --- | --- |
| 核心服务闭环覆盖率 | 100% | 完整度不一 | 一期范围均有可验收主流程 |
| 关键任务完成率 | ≥80% | 试点前建立 | 完成目标产物或业务动作 |
| 工具调用成功率 | ≥95% | 当前需统一统计 | 参数、执行和结果均正确 |

**项目验收标准**

| 验收指标 | 验收标准说明 | 验收方 |
| --- | --- | --- |
| 业务闭环 | 核心场景可从自然语言进入并完成任务 | 产品、业务 |
| 安全与正确性 | 高风险用例 100% 通过，不伪造业务结果 | 专家、产品、QA |
| 稳定与体验 | Run 成功率 ≥98%，5-10 并发稳定，App 正确渲染 | 技术、QA、SRE |

### 项目方案对比选择

| 方案 | 描述 | 成本 | 风险 | 推荐度 |
| --- | --- | --- | --- | --- |
| A（推荐） | 统一主智能体 + 动态技能 + 全局工具 + 结构化产物 | 中高 | 需要较强工程治理 | ★★★★★ |
| B（保守） | 每个服务建设独立机器人或固定流程 | 高 | 重复建设、跨场景割裂 | ★★★ |
| C（降级） | 只做通用聊天和知识库问答 | 低 | 无法完成业务闭环 | ★★ |

**推荐方案理由**

- 当前工程已经具备方案 A 的平台基础，继续收敛成本低于重新拆分。
- 不采用 B：用户旅程跨越孕期、哺乳和设备，独立机器人会重复建设并割裂上下文。
- 不采用 C：只能回答问题，无法完成记录、计划、设备和卡片任务，不能解决核心问题。
